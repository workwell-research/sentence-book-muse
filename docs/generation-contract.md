# 生成データ仕様 — sentence_book_page_v1

更新: 2026-10-27 JST

これは今回の新規版で定義した仕様。受領した作り直し設計書の必須フィールドと方針を基にするが、参照先の lesson-schema-v2 本体は提供されておらず、本人の「そのファイルはなさげ」を受けて待機を終了した。旧v2の復元・互換実装とは扱わない。

## 関心領域と題材（本人の追加方針・2026-10-27）
最初に関心領域を複数選ぶ。候補は8種類の入口であり、固定分類ではない。自由入力・あとで選ぶ・後から変更・指定解除に対応する。選択だけでバインダーは作らない。

- 関心はこのブラウザの独立した保存キーに保持し、既存のメモを変更しない。
- 生成時は選んだ関心を優先して場面・語彙・問いを考える。具体的な今回の話題がある場合はそれを尊重し、無理に関心へ関連づけない。
- 話題が空欄でも関心から題材を考えられる。関心も話題も空の生成依頼は拒否する。
- SNSに書くような短い雑談・冗談・ぼやきも、希望を伝える、理由を説明する、頼む、予定を調整するといった実用場面へ広げる。投稿の逐語訳だけで終えず、投稿者や文章の価値を評価しない。
- 入力にない経歴・資格・診断・好みを事実として補わない。足りない情報は中立的・仮定の場面として扱う。
- SNSアカウントの接続や自動収集は今回実装しない。本人が入力した短文だけを扱う。

実装: `shared/interests.ts`（関心の検証）、`shared/generation-request.ts`（依頼）、`functions/lib/muse-prompt.ts`（モデルへ渡すメッセージ作成）。プロンプトとデータを分離し、題材や関心の文言はJSONデータとして渡す。これは生成品質やプロンプト注入への完全な耐性の保証ではない。

依頼は draft_id、topic（0〜2000文字）、interests（0〜12件・各1〜40文字・重複なし）、level、native_language、based_on_learning_state_version、binders（id/title/description、1依頼あたり最大100件、ID重複なし）。12件は関心設定の入力上限、100件は依頼サイズの上限であり、本棚のテーマ数を固定するものではない。変更した題材・設定で生成するときは新しいdraft_idを発行し、同じ内容の再試行では保持する。

関心選択とローカル保存は実装済み。2026-10-29に画面からの実送信とMeta Model API（muse-spark-1.3）呼出を接続し、ローカルで実生成を確認した。短文から役立つ教材になるかは、まだ数件の実例でしか見ていない。

## 分類方針
- 初期バインダーは0冊。テーマ名・冊数を固定しない。旧5テーマは投入しない。
- 最初のページから、内容に合う新規バインダーを提案する。本人が名前・説明を確認し、明示承認して初めて作成する。
- 既存バインダーが合うときはそこへの追記を優先する。本人は採用前に振り分け先を変更できる。
- 生成結果は提案であり、検証成功だけでバインダーやページを作らない。
- モデルへ渡す一覧は実在するid/title/description。モデルが勝手なIDを返したら拒否する。固定テーマの列挙型は持たない。
- Binderのoriginは新規版では `approved-new`。以前の初期 `preset` 案は撤回。バインダー・ページの安定IDはアプリ側で発行する。

## データ契約
実装正本: `shared/lesson-schema.ts`。Zodのstrict objectを用い、未知のキー・型変換・不正な構造は受け入れない。JSON Schemaも同じ定義から生成する。

| 必須キー | 定義 |
| --- | --- |
| draft_id | アプリが依頼前に発行するUUID。同じ依頼の再試行では維持し、応答が一致するか検証 |
| title | 空白だけではない1〜120文字 |
| level | A2 / B1 / B2。依頼値と一致 |
| native_language | ja / en / es / fr / ko / zh。現行入力UIの対応言語に合わせ、依頼値と一致 |
| sentences | 4〜12件。目標8文。各要素はen/nativeの組、それぞれ1〜500文字 |
| questions | 1〜2件。各要素はen/nativeの問いと、sample_answer:{en,native}の回答例。それぞれ1〜500文字 |
| review_items | 0〜4件。expression（1〜120文字）、native（説明1〜300文字）、sentence_index（0始まりの文番号）。学習者が間違えた事実を表す項目ではない |
| estimated_minutes | 1〜60の整数。モデルの目安であり、実測時間ではない |
| based_on_learning_state_version | 依頼時の学習状態バージョン（0以上の安全な整数）。未提供ならnull。応答と完全一致 |
| filing | 下記のどちらか1種類 |

`filing`:
- 既存: `{kind:"existing", binderId, reason, sceneTags}`
- 新規提案: `{kind:"new", newBinder:{title,description}, reason, sceneTags}`
- binderIdはUUIDかつ依頼時の一覧に存在するID。newBinderはtitle 1〜80文字、description 1〜240文字。
- reasonは説明言語の短い理由（1〜400文字）、sceneTagsは1〜5件、各1〜40文字。タグの件数はテーマ数の上限とは別。
- 両方の振り分け先を同時には持てない。新規案にIDを生成させない。

4〜12文などの上限、questions/review_itemsの内部構造は今回定義した実装判断であり、未取得の旧仕様からの引用ではない。

## 検証と採用の境界
`validateLessonDraft` は構造に加え、依頼のID・レベル・言語・学習状態版、既存バインダーの存在、復習の文番号を確認する。サーバーとブラウザの両方から使える副作用のない関数。意味・翻訳の正確さや自然さは構造検証だけでは保証できない。

2026-10-29時点: Metaアダプター（`functions/lib/model-client.ts`）、`/api/generate` でのサーバー側検証、ブラウザ側の再検証、プレビュー、`sentence-book-muse:pending-drafts:v1` への保存までを接続した。Zodから生成したJSON SchemaはMetaの構造化出力で受理された。採用は同日遅くに実装: `src/lib/library.ts` の `fileDraft` が本人の明示した決定（新しい本を作る／既存の本に追加）だけでページを保存し、同じdraft_idの二重採用・一覧にない本・空の本名・読めない保存データを拒否する。生成依頼には実在するバインダーの一覧を渡し、サーバーはその一覧にあるIDの提案だけを受け付ける。練習への接続は未実装。キー未設定の環境では `/api/generate` は503を返す。

今後、サーバーとブラウザの両境界でこの関数を実行する。採用時は最新の本棚でも振り分け先を再確認し、sourceDraftIdと採用済みIDを同じ保存状態へ記録する。二重採用を拒否し、保存失敗時に成功扱いしない。新しい本の明示承認はページ採用と区別する。これは次工程であり、draft_idの形式検証だけでは実現しない。

プロンプトの学習要約は端末に記録された実績だけから作り、忙しさ・苦手・理解度を推測しない。元の話題・学習者の実データをテスト資料にコピーしない。

参考: [Zod公式JSON Schema変換](https://zod.dev/json-schema)、[スキーマ定義](https://zod.dev/api)。
