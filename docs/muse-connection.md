# Personal Muse connection

Implementation started 2026-10-30. This document describes the implementation and configuration contract; current deployment/verification status is in PROJECT_STATUS.md. The earlier personal prototype is not changed.

## Learner flow

1. Open `/connect`, sign in with an email confirmation code, and enable your personal inbox. Anyone may connect their own Muse; no invitation code is required.
2. Preview the learning summary from this browser, then explicitly publish it. Updates are manual. Stopping sharing clears the server snapshot and blocks new deliveries.
3. Use the connection-key section to copy the public instructions to Muse, choose read/delivery permissions, and issue a 30-day key. Paste it directly into Muse’s secure API-key field, never into chat. The key is displayed once; the server stores only its SHA-256 digest. The OAuth path remains supported for compatible clients, but the current Muse OAuth link fails before our consent page. Actual authenticated Muse key compatibility remains to be checked.
4. Ask Muse to read the guide and current state, then deliver a draft. A schedule is a separate learner choice; the app does not create one.
5. Review the cloud inbox and explicitly file or discard. Filing copies a lesson into this browser's existing library. After a successful local write, the server receives a completion receipt. A failed receipt can be retried without a second local copy. Resolving an inbox item removes its body from the common inbox on every device; local books/practice are not synchronized.

## Server boundary

- Separate Supabase project: `wgyyfxlabbzhnrbtwmcc`, Tokyo, `sentence-book-muse`, in `workwell-research's Org`. Created at the tool's quoted $0/month. Existing project `mmnbymoivpzzbvmdshlb` is untouched.
- Four tables live in `muse_private`, with RLS enabled and no browser roles granted schema/table access. Deliberately no RLS allow policies: the advisor's four INFO notices reflect default deny. Neither anonymous nor authenticated roles can invoke the public gateway functions.
- Pages alone uses `SUPABASE_SECRET_KEY`. It verifies the JWT with Supabase Auth, then checks issuer, audience `authenticated`, expiry, user and session/client IDs. The database independently checks the live Auth session, confirmed email, ban, enabled membership and the matching OAuth client session. Auth grant revocation deletes that client’s sessions, so the live check rejects revoked tokens. Every row operation uses that verified user ID. App grants are separate from the OAuth OIDC scopes.
- `muse_gateway` uses security-invoker and service-only execute access, a fixed operation list, and a transaction advisory lock per user. It has column-only read grants on `auth.users` and `auth.sessions`. Managed OAuth client/consent tables are not directly readable by service_role; the server validates clients through the Auth admin API and stores the verified display name with each app grant. No SECURITY DEFINER or arbitrary browser-provided table filters.
- Personal sessions alone may enroll, publish/unshare, resolve or manage grants/keys. OAuth sessions and connection keys cannot call those operations. Grant creation verifies the authorization request with Auth and takes the client ID from its response, not caller input. App revocation denies access immediately; the browser also requests Auth grant revocation to stop token refresh.
- The owner opened personal Muse enrollment to everyone on 2026-10-30. Verified email, a live personal session and per-client consent still protect each account. The applied migration retains the legacy internal error name `invitation_required` for a missing/disabled membership ; the cookie gate was in the server handler and is now removed. The follow-up migration also corrects the historical invitation-cookie comment. No table permissions or RLS were relaxed.
- Paid generation/lookup keep their existing invitation-cookie guard. Muse delivery does not call the app owner's model API.

## Personal connection keys — 2026-10-30

Muse’s actual `credentials.request_api_access` API-key flow opened a secure API-key input field after its Link/Next steps. No real key was entered at this checkpoint. This establishes the input UI, not successful credential injection or MCP compatibility. Its reported placement is `bearer_header`, scoped only to `sentence-book-muse.pages.dev`. The public copyable instructions are generated by `src/ConnectionKeys.tsx`; they explain secure entry, REST endpoints and the optional MCP alternative, and do not contain credentials.

- A verified direct account explicitly chooses summary read and/or draft delivery, both initially unchecked. At least one is required. Only the direct account can create/list/revoke its keys. A delegated key or OAuth session cannot manage accounts, keys, summaries, inbox processing, or local books.
- The server creates a cryptographically random 256-bit `sbm_` bearer token, returns it once with `Cache-Control: no-store`, and sends only SHA-256 to the database. The browser keeps the raw key in mounted state, masks it by default, and clears it on dismiss/logout/account change/reload. It is not put in localStorage. A copied key can remain on the learner's clipboard; they paste it directly into the dedicated Muse field.
- Fixed validity: 30 days. At most five active keys per user, enforced transactionally under the same advisory lock as revoke/delivery. Expired rows are removed when another key is issued. Logout of the app does not revoke an independent integration key; the UI says so. Lost keys are revoked and replaced, never recovered.
- Each operation rechecks the hash, key ID, owner, expiry, enabled membership and verified/unbanned user. Revocation blocks even a request whose initial identity lookup already succeeded. Direct-session and OAuth checks remain intact. Key metadata lists exclude user ID/hash/raw key.
- `GET /api/muse/guide` is public. Authenticated `POST /api/muse/learning-state` takes `{delivery_date}`; `POST /api/muse/deliver` takes the existing validated delivery object. `/mcp` accepts the same key. The key does not authorize owner-funded `/api/generate` or `/api/lookup`.

The gateway's optional sixth argument preserves old five-argument callers during rollout. It was applied to the new project only. ## Tools and receipts

`get_lesson_guide` returns the shared lesson contract and instructions. `get_learning_state` returns only the explicitly shared snapshot, version, pending count, and a stable daily draft ID for the learner-selected date. Accuracy and time spent are unknown (`null`), not estimated from inactivity. `deliver_page_draft` accepts a strict `{contract, delivery_date, draft}` object with `sentence_book_page_v1` content. The ID derives from user/date; level, language, version and binder IDs must match the current snapshot. New deliveries accept dates from seven days ago through tomorrow (UTC allowance covers local date differences).

Delivery is idempotent by user/draft ID plus canonical payload hash. Same payload returns a duplicate receipt even after filing/discard; changed content conflicts. Pending inbox capacity is 50. A processed item keeps only receipt metadata/hash, not the lesson body. There is no auto-filing. Request bodies are capped at 64KiB; D1 limits MCP/REST calls to 30/min, 500/day per caller address and 10,000/day total, failing closed on storage errors. These are coarse usage limits, not a provider spending budget.

MCP uses the official TypeScript SDK, per-request stateless HTTP, with legacy 2025 streamable HTTP support. Protected-resource metadata is at `/.well-known/oauth-protected-resource/mcp`. The default Supabase `authenticated` audience is project-wide; live client grants and operation checks supply the application boundary. This is not a claim that Supabase tokens have a resource-specific MCP audience.
