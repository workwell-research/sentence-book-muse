# ユーザーの Muse から教材を届ける「ルーチン」設計 — 2026-10-30

目的: 学習者本人の Muse（Muse アプリ）が、本人の文脈（昨日の会話・今日の予定・興味）を材料に、
The Sentence Book の教材仕様どおりのページを作り、アプリへ届けることを「毎朝のルーチン」にする。

前提（2026-10-30 時点の新規版の実装状態）:
- 生成契約 `sentence_book_page_v1` が正本（`shared/lesson-schema.ts`、Zod → JSON Schema）。
  依頼側は draft_id / topic / interests / level / native_language / based_on_learning_state_version / binders（一覧）。
  応答側は sentences / questions / review_items / estimated_minutes / filing（既存 or 新規提案）。
- アプリ内生成（Meta Model API）は接続済み。生成 → プレビュー → 下書き保存（pending-drafts）→
  本人の明示決定でのみ採用（fileDraft、二重採用拒否）まで実装済み。
- ただし新規版の保存は今のところブラウザ内（localStorage）のみ。**ここがルーチン化の前提条件になる**（§4）。

## 1. 仕様の「渡し方」— 接続すること自体が仕様の配送になる

仕様をユーザーが手で Muse に貼るのではなく、アプリ側が **MCP サーバー** として仕様を広告する。
ユーザーは自分の Muse で「接続する」だけで、スキーマと作り方が Muse に届く。

公開するツールは3つだけ（権限は旧プロトタイプで合意した2権限＋ガイド）:

| ツール | 役割 |
| --- | --- |
| `get_lesson_guide` | 教材の作り方ガイドを返す。レベル感（A2/B1/B2 の文の単純さ）、文数（目標8文・4〜12）、questions / review_items の役割、filing 提案の作法、適応ルール（§3）を文章で渡す。スキーマだけでは伝わらない「作り方」はここに置く |
| `get_learning_state` | 学習状態の**要約のみ**： state_version、未消化の下書き／未練習ページ数、直近のペース、復習候補（Words to keep）、現在のバインダー一覧（id/title/description）。全履歴は渡さない |
| `deliver_page_draft` | `sentence_book_page_v1` の下書きを1件受け取り、サーバー側でも同じ Zod 検証を通して受信箱に入れ、受領証（draft_id・検証結果）を返す。採用はしない |

- 契約名とバージョン（`sentence_book_page_v1`）をツール定義に含め、サーバーは未知のバージョンを拒否する。
- 認証は OAuth（DCR）の個人接続。スコープは「要約の読み取り」と「下書きの配送」のみ。
  旧プロトタイプ（Typing）で Claude との OAuth 接続・実配達・受信箱プレビューまで実証済みの方式。

補助経路（MCP 接続が使えないクライアント向け）: アプリが「指示カード」（ガイド要約＋スキーマへの
リンク＋接続手順）を発行し、ユーザーが Muse に一度貼る。ただしルーチン化には MCP 接続が本命。

## 2. ルーチンの実行手順（ユーザー Muse 側の定時タスク）

ユーザーが自分の Muse に一度だけ頼む：「毎朝7時に、Sentence Book の今日のページを作って送って」。
Muse 側に定時タスクができ、毎回この順で動く:

1. `get_learning_state` で要約を取得（state_version、積み残し量、バインダー一覧、復習候補）。
2. Muse が知っている本人の文脈から今日の話題を決める（昨日の会話、今日の予定、興味プロフィール）。
   アプリ側の生成と違い、topic を本人が書く必要がないのがこの経路の価値。
3. 適応ルールで量と難易度を決める（§3）。
4. ガイド＋スキーマに従って下書きを生成。draft_id は日付由来の決定的 ID（再実行しても同じ ID）。
5. `deliver_page_draft` で配送。検証エラーが返ったら1回だけ直して再送、それでも駄目なら諦めて報告。
6. Muse のチャットで本人に一行報告（「今日のページを届けました：〈タイトル〉」）。

**ルーチンが自動化するのは「作成と配送」まで。** アプリでのプレビューと採用（ファイリング確定）は
従来どおり本人の明示操作。朝起きたら下書きが「仕分けを待つページ」に届いている、が体験の完成形。

## 3. 適応ルール（ガイドに明記する）

山下の既存ルール（2026-10-25）をガイド側の判断基準として埋め込む:

- 下書きや未練習ページが積み上がっていたら、新規ページは作らず復習中心の1ページにするか、配送自体を止めて報告する。
- 短いセッションで自力正解が続いていれば、次は一段階だけ難しくする。
- よく間違える語句・表現は、別の話題・文脈で繰り返し登場させる（review_items と連動）。
- 止まっている理由が「忙しさ」なら量を減らす。「難しさ」が理由ならレベルを下げる。両者を混同しない。

## 4. アプリ側に必要な追加実装（前提条件）

新規版は現在 localStorage のみ。アプリが閉じている間に届くルーチンには、次が必須:

1. **アカウントとクラウド受信箱**: ユーザーアカウント＋サーバー側 inbox（下書きの置き場）。
   アプリを開いたときに inbox → pending-drafts へ取り込み、既存のプレビュー／採用フローに合流させる。
2. **MCP エンドポイント**: 上記3ツールの実装。検証は既存の `validateLessonDraft` をサーバー側でも使う。
3. **学習状態の集計**: `get_learning_state` 用に、state_version の採番と要約の組み立て
   （version フィールドは契約に既にあるので、集計側を作ればよい）。
4. **重複排除**: draft_id をキーに inbox 側でも二重配送を弾く（採用側の二重採用拒否は実装済み）。

## 5. 段階導入

- Phase 1（手動往復）: ユーザーが Muse に「今日のページを作って送って」と頼み、配送→プレビュー→採用が通る。
- Phase 2（ルーチン化）: ユーザーが Muse 側で定時タスクを設定し、数日回して量・質・失敗時の挙動を見る。
- Phase 3（製品化）: アプリの「Muse とつなぐ」導線が、接続＋ルーチン設定用の定型文
  （「毎朝7時に…」の指示文そのもの）を発行し、ユーザーは貼るだけで Phase 2 まで終えられる。

## 6. ハッカソン提出との切り分け

- 今回の提出の本体はアプリ内生成（実装済み）＋ファイリング＋練習。ルーチンはその先の拡張。
- もし期間内に新規版へ MCP エンドポイントまで実装できれば、それは期間内の新規作業として
  デモに含められる（「自分の Muse が今朝、予定から作ったページが届いている」は強い一場面）。
  ただし締切（11/5 11:00 JST）に対しては、デプロイと動画を優先し、これは余力枠。
- README／ピッチでは、旧プロトタイプで MCP 配送の往復が実証済みであることと切り分けて書く
  （新規版のルーチンは「設計＋段階計画」として提示し、実装済みと誤認させない）。
